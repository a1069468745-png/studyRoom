## 1. 设计目标

本阶段目标是把产品定义收敛为可实现、可维护、可测试的技术方案，确保：

- 系统架构清晰，边界可拆分。
- 数据模型稳定，后续可扩展。
- API 规格明确，前后端可并行开发。
- 权限和审核链路可追踪。
- 关键风险与取舍已记录。

## 2. 方案结论

### 2.1 架构形态

采用微服务优先的架构，按业务域拆分为独立服务：

- `gateway`：统一入口、路由、限流、鉴权前置
- `auth-service`：登录、令牌、会话、权限
- `knowledge-service`：知识点、教材版本、内容管理
- `question-service`：题目、标签、解析、审核
- `paper-service`：组卷规则、模板、试卷生成
- `exam-service`：考试计划、考试实例、答卷
- `grading-service`：批改、复核、自动判分
- `analytics-service`：成绩分析、错题、知识点掌握
- `audit-service`：审计日志、操作留痕、发布追踪
- `job-service`：异步任务、重试、状态跟踪
- `file-service`：文件、图片、视频资源

服务之间通过 HTTP/OpenFeign 进行同步调用，异步场景通过任务表和事件记录推进，首版不强制引入 MQ。

### 2.2 技术栈

推荐主栈：

- 后端：Java 21
- 服务框架：Spring Boot 3
- 微服务治理：Spring Cloud Alibaba 2023.x
- 注册与配置：Nacos
- 网关：Spring Cloud Gateway
- 服务调用：OpenFeign
- 流控与熔断：Sentinel
- 持久层：MySQL 8
- 缓存：Redis
- 文件与视频资源：MinIO
- 任务执行：数据库任务表 + 后台 worker
- 权限：Spring Security
- 数据迁移：Flyway
- 对象转换：MapStruct
- 可观测性：Micrometer + 日志 traceId 贯通

理由：

- Java 21：LTS 版本，性能和并发能力成熟，适合长期维护。
- Spring Boot 3：企业级生态成熟，适合快速搭建独立服务。
- Spring Cloud Alibaba 2023.x：一次性补齐注册、配置、路由、调用治理和流控能力。
- Nacos：同时承担注册中心和配置中心，减少组件数量。
- Gateway：统一入口、鉴权前置、限流和路由控制。
- OpenFeign：服务间调用声明式，降低接口耦合成本。
- Sentinel：支持限流、熔断、降级，适合微服务早期防护。
- MySQL 8：事务和结构化数据能力稳定，适合考试与题库类核心数据。
- Redis：承担缓存、幂等键、短期状态和热点数据，加速查询与任务调度。
- MinIO：S3 兼容，适合图片和视频资源管理，后续容器化也容易迁移。
- Flyway：数据库演进可追踪，便于多服务分 schema 的变更管理。
- Spring Security：权限与认证能力成熟，适合资源归属和审核流。
- MapStruct：减少 DTO/VO 映射样板代码，降低服务间数据转换成本。
- 任务表 + worker：足够支撑首版异步组卷、分析和媒体处理，不需要过早引入 MQ。

### 2.3 关键设计原则

- 先服务边界，后部署形态。
- 先接口契约，后服务实现。
- 先统一认证与审计，再扩展服务数量。
- 先同步调用 + 任务表，后补 MQ。
- 先为容器化预留无状态约束，但本阶段不实施容器化。
- 先保证可追踪，再追求自动化覆盖率。

### 2.4 为什么本阶段不引入 MQ

不引入 MQ 不是否定消息系统，而是当前阶段性决策：

- 目前异步场景主要是组卷、分析、文件处理，数量有限，任务表 + worker 足够。
- MQ 会额外引入部署、监控、重试、幂等、顺序、死信和补偿成本，测试场景也会指数增加。
- 现在先把微服务边界、幂等键、任务状态、审计链路固定下来，后续再引 MQ 更稳。
- 当跨服务事件明显增多、通知扇出增大、异步吞吐超过任务表可承受范围时，再补 MQ 更合理。

如果现在引入 MQ，短期收益有限，但会显著抬高首版复杂度和故障面。

### 2.5 性能与额外技术判断

当前这套技术栈足以覆盖“几十到几百并发、秒级组卷、秒级到分钟级分析”的目标，前提是：

- 网关和服务端做好连接池、缓存、分页和幂等控制。
- 热点查询走 Redis 或本地缓存。
- 组卷和分析走异步任务，不阻塞请求线程。
- 题库检索、关联查询和分析报表按需分页，不做全表扫描。

首版暂不必须新增的技术：

- MQ：现在不需要。
- Elasticsearch/OpenSearch：如果后续题库检索和模糊搜索规模明显增大，再补。
- Kubernetes：容器化阶段再引入。
- 分布式事务框架：当前以本地事务 + 幂等 + 补偿控制为主。

结论：当前栈满足首版性能要求，但前提是架构上保持“微服务边界清晰 + 异步任务化 + 缓存优先”。

## 3. 已确认边界

- 首版以中学场景为主。
- 自动批改采用“客观题尽量自动、主观题人工兜底”。
- 视频解析不进入首版验收，只保留预留/草稿能力。
- 内容来源按可抓取与整理方向推进，授权白名单后补。
- 服务逻辑上按微服务设计，物理部署可先非容器化落地，后续平滑迁移到容器化。

## 5. 风险与假设

- 假设现阶段并发处于几十到几百的量级。
- 假设首版题库、考试、分析规模可由单库或同一 MySQL 集群中的服务独立 schema 承载。
- 假设异步任务可以接受秒级到分钟级完成，不要求强实时。
- 假设后续微服务数量增长时，服务边界不需要重做，只需要补齐基础设施。
- 风险已登记到 `ai/risk-register.md`。
