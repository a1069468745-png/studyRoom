## 1. 目标

- 明确前端主栈，满足 Web 客户端与管理端并行开发需求。
- 明确前端工程边界，支撑老师、学生、管理员三类角色主链路。
- 明确路由、状态、接口层、权限和测试策略，避免阶段 4 并行开发时口径漂移。
- 保持与网关、统一错误结构、任务状态结构和权限模型的一致性。

## 2. 技术栈

### 2.1 结论

前端默认采用 Vue 技术栈，不单独引入第二套前端框架。

推荐组合：

- 框架：Vue
- 语言：TypeScript
- 构建工具：Vite
- 路由：Vue Router
- 状态管理：Pinia
- HTTP 客户端：Axios
- 组件库：Element Plus
- 表单校验：基于组件库表单能力 + 业务校验封装
- 图表：ECharts
- 单元与组件测试：Vitest
- 页面联调与端到端测试：Playwright
- Mock 能力：基于本地 fixture/mock server 的契约模拟

### 2.2 选型理由

- Vue：满足用户前置要求，适合表单、管理端、规则配置器和中后台页面快速落地。
- TypeScript：便于把后端 DTO、错误码、任务状态转成前端可校验的类型约束，降低并行开发时的契约漂移风险。
- Vite：开发反馈快，适合阶段 4 的多页面并行开发和 mock 联调。
- Vue Router：适合老师/学生客户端与管理员端的路由守卫、按角色分区和按功能切片组织。
- Pinia：足够支撑登录态、权限摘要、任务轮询状态、全局字典和 UI 状态，不需要引入更重的状态方案。
- Axios：便于统一实现鉴权头、`traceId` 透传、错误拦截、任务轮询封装和超时控制。
- Element Plus：覆盖表单、表格、树、对话框、抽屉等中后台高频组件，适合课程树、题库审核、规则模板治理等场景。
- ECharts：适合考试分析、知识点掌握度、趋势图等数据可视化场景。
- Vitest + Playwright：分别覆盖组件/页面逻辑和三角色主链路，符合当前阶段 4 的分层测试策略。

## 3. 工程结构

### 3.1 应用划分

- `web-client`：老师与学生共用的 Web 客户端。
- `admin-console`：管理员端。
- `frontend-shared`：共享类型、API client、错误处理、任务状态、权限工具、通用 hooks/组合式函数。

### 3.2 目录建议

- `apps/web-client`：学生与老师页面、路由、业务模块。
- `apps/admin-console`：管理员端页面、路由、业务模块。
- `packages/shared`：类型定义、常量、API 封装、任务查询封装、权限工具。
- `packages/mock`：fixture、mock handler、联调前假数据。

### 3.3 模块边界

- 客户端与管理端共享契约层，不共享角色专属业务页面。
- 权限、错误处理、任务查询、字典和课程树选择器优先沉淀到共享层。
- 业务页面按知识库、题库、组卷、考试、分析、视频审核等域切分，避免单文件过大。

## 4. 路由与权限

### 4.1 路由分区

- 客户端：`/client/*`
- 管理端：`/admin/*`
- 公共页：登录、错误页、无权限页、任务结果页

### 4.2 权限模型映射

前端只负责“展示层守卫”和“体验层收敛”，不代替后端鉴权。

- 角色维度：管理员、老师、学生。
- 资源归属维度：通过 `GET /api/common/me` 和业务接口返回的授权摘要控制菜单、页面和操作显隐。
- 流程状态维度：根据草稿、审核中、已发布、已停用等状态决定操作按钮可用性。

### 4.3 路由守卫要求

- 未登录用户统一跳转登录页。
- 已登录但无权限用户跳转无权限页，不允许仅靠隐藏按钮替代路由限制。
- 视频草稿、审核页、考试结果页等页面必须根据资源归属和状态双重控制。

## 5. 状态管理

### 5.1 Pinia Store 划分

- `auth-store`：登录态、当前用户、角色、权限摘要。
- `dictionary-store`：字典、教材版本、课程树基础缓存。
- `task-store`：异步任务状态轮询、失败原因、重试状态。
- `ui-store`：全局 loading、通知、布局折叠、主题变量。

### 5.2 状态原则

- 业务详情优先按页面获取，不把大对象长期堆在全局 store。
- 任务状态统一从公共任务接口查询，避免每个页面重复实现轮询逻辑。
- 权限相关状态以服务端结果为准，前端缓存只做体验优化。

## 6. 接口层与错误处理

### 6.1 API Client 规则

- 所有请求统一经由网关路径发起，不直接访问内部微服务地址。
- 统一注入鉴权头、客户端标识和必要的请求追踪信息。
- 统一处理分页结构、错误结构、任务状态结构。

### 6.2 错误处理规则

对齐 `docs/03_design/api-spec.md`：

- 统一识别 `code/message/traceId`
- 对 `AUTH_UNAUTHORIZED`、`AUTH_FORBIDDEN`、`VALIDATION_FAILED`、`TASK_FAILED` 等错误做统一页面或消息处理
- 任务型接口优先展示任务状态与失败原因，不把异步失败伪装成同步成功

### 6.3 Mock 与契约同步

- 前端 mock/stub 必须来自当前 API 规格和已确认决策，不允许自由猜字段。
- DTO、错误码、任务状态、分页结构变化后，必须同步更新共享类型和 mock 数据。
- `DEV-008` 前必须完成一次 mock/真实接口差异清单收口。

## 7. 页面与组件策略

### 7.1 客户端

- 学生：首页、知识点内容、考试作答、成绩与解析、视频播放。
- 老师：组卷、模板预览、考试组织、分析查看。

### 7.2 管理端

- 课程树维护
- 知识内容管理
- 题库审核
- 视频草稿审核与发布
- 审计与基础字典入口

### 7.3 通用组件

- 课程树选择器
- 任务状态面板
- 审核记录时间线
- 规则模板表单块
- 错误态、空态、无权限态

## 8. 测试与验证

### 8.1 自动化测试

- Vitest：组件逻辑、组合式函数、store、API 封装、权限工具
- Playwright：学生、老师、管理员三角色主链路

### 8.2 联调验证

- 先使用 mock/stub 做页面级集成验证
- 再在 `DEV-008` 做真实接口闭环验证
- 契约变更后先回归共享类型和 API client，再回归页面

## 9. 部署与构建要求

- 前端产物默认构建为静态资源，通过网关或独立静态服务对外提供。
- 客户端与管理端支持独立构建与独立发布，避免彼此阻塞。
- 环境配置通过构建时变量和运行时配置文件注入，不在代码仓库中硬编码敏感地址或密钥。

## 10. 非目标范围

- 不引入第二套前端框架。
- 不做原生 App、小程序或桌面端。
- 不在首版引入复杂微前端拆分。
- 不为首版单独建设设计系统平台，优先基于组件库和共享组件收敛。
