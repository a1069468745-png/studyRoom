## 1. 架构概览

系统采用微服务架构，按业务域拆分服务，通过网关统一入口，通过 Nacos 管理注册与配置，通过 OpenFeign 进行服务间调用。首版视频解析作为验收范围的一部分，但只要求形成最小闭环。

### 前端应用

- `web-client`：老师与学生共用的 Web 客户端，采用 Vue + TypeScript + Vite。
- `admin-console`：管理员端，采用 Vue + TypeScript + Vite。
- `frontend-shared`：共享类型、API client、错误处理、任务状态、权限工具与通用组件能力。

### 核心服务

- `gateway`：统一入口、路由、鉴权前置、限流
- `auth-service`：登录、会话、令牌、角色与资源权限
- `knowledge-service`：知识点、教材版本、内容管理
- `question-service`：题目、标签、解析、审核
- `paper-service`：组卷规则、试卷生成、模板版本
- `exam-service`：考试计划、考试实例、答卷
- `grading-service`：客观题判分、主观题批改、人工复核
- `analytics-service`：成绩分析、错题、知识点掌握
- `audit-service`：审计日志、操作留痕、发布追踪
- `job-service`：异步任务、重试、状态跟踪
- `file-service`：文件、图片、视频资源

## 2. 部署形态

### 首阶段

- 逻辑上是微服务，物理上可以先在同一台机器或同一网络内部署多个服务进程
- 每个服务独立进程、独立配置
- 同一 MariaDB 集群内按服务独立 schema 或 database 管理（MySQL 协议兼容）
- Redis 用于缓存、幂等键和轻量任务协调
- MinIO 用于文件、图片、视频资源
- 手工备份

### 后续演进

- 支持容器化部署
- 支持水平扩容
- 支持定时备份
- 支持容灾与升级窗口
- 支持拆包/拆模块部署
- 支持独立服务灰度与回滚

## 3. 请求链路

### 3.1 知识点查询

前端 -> 网关 -> 知识库服务 -> 数据库/缓存 -> 返回结果。

### 3.2 组卷

前端提交规则 -> 网关 -> 组卷服务 -> 规则校验 -> 异步创建组卷任务 -> 后台 worker 计算试卷 -> 落库 -> 前端通过统一任务接口轮询/查询任务状态。

组卷服务在规则校验阶段必须先解析课程范围：

- `ALL_SUBJECT`：全学科
- `UNIT_SET`：指定单元集合
- `CHAPTER_SET`：指定章节集合
- `NODE_RANGE`：课程树节点区间
- `KNOWLEDGE_SET`：指定知识点集合

所有范围输入都必须在服务端落为明确的 `UNIT_SET`、`CHAPTER_SET`、`NODE_RANGE` 或 `KNOWLEDGE_SET`。

### 3.3 考试与批改

考试计划创建 -> 考试服务 -> 生成考试实例 -> 学生作答 -> 交卷 -> 批改服务 -> 分析服务 -> 结果展示。

### 3.4 视频资源

管理员发起视频草稿生成 -> 异步生成草稿任务 -> 审核 -> 发布 -> MinIO 存储 -> 学生端按授权在线播放。

### 3.5 权限判定链

所有受保护资源统一按三层判定：

- 角色：管理员、老师、学生、审核人、服务身份
- 资源归属：班级、教学授权、考试参与范围、资源所有者范围
- 流程状态：草稿、待审核、已通过、已发布、已停用

示例：

- 老师仅能访问其 `teaching_assignment` 覆盖范围内的题库、模板、考试与分析数据。
- 学生仅能访问自己参与的考试、成绩、知识点内容和已发布且授权的视频。
- 未审核通过的视频草稿仅管理员与审核人可见。

### 3.6 前端请求与任务链路

- 前端统一通过网关访问客户端和管理端接口，不直连内部服务。
- 前端统一消费 `code/message/traceId` 错误结构和公共任务状态结构。
- 组卷、分析、视频草稿生成等异步流程统一通过公共任务查询接口轮询状态。
- 前端 mock/stub 必须与 API 规格和已确认决策同步维护，联调前先完成契约校验。

## 4. 设计取舍

### 方案 A：微服务

优点：

- 边界清晰
- 未来容器化和水平扩容成本低
- 业务域可独立演进

缺点：

- 首版运维复杂度高于单体
- 分布式事务和调用治理需要提前约束

### 方案 B：前后端分离的单体

优点：

- 接口边界清晰
- 前后端并行开发方便

缺点：

- 未来从单体改微服务的改造量大
- 分布式边界后补会导致测试场景扩散

### 方案 C：模块化单体

优点：

- 兼顾可维护性和交付速度
- 未来可平滑拆分
- 更适合当前并发和规模预期

缺点：

- 未来仍要经历单体拆分
- 迁移到微服务时改造量仍然大

推荐：方案 A。

## 5. 错误与降级

- 组卷失败时返回任务失败状态和可读原因。
- 历史真题不足时自动降级，不允许静默失败。
- 批改无法自动判定时进入人工复核队列。
- 视频资源不可用时返回可追踪错误并记录审计。
- 微服务之间调用必须带 `traceId` 和幂等标识。
- 分布式调用失败时，优先返回可恢复错误而不是隐式重试风暴。
- 所有异步任务失败时返回统一任务失败结构，包含失败原因、是否可重试和 `traceId`。

## 6. 约束

- 统一鉴权。
- 服务间调用需要服务身份校验和最小权限。
- 审计日志不可修改，仅追加。
- 软删除默认启用，但关键业务删除需记录操作人和原因。
- 关键链路必须可追踪到用户、时间、资源和结果。
- 不同角色的访问控制必须落到数据归属实体，不允许只依赖接口路径区分权限。
- 前端只做展示与交互层守卫，不代替后端鉴权和资源归属判定。
